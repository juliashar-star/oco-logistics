# СДЭК — отмена заказа. Исследование от 2026-08-11

**Источник:** файл OpenAPI «Клиентский протокол интеграции с логистикой», version 1.0.0
(`servers`: `https://api.cdek.ru` — рабочая среда, `https://api.edu.cdek.ru` — тестовая).
Прочитан целиком 11.08.2026. Всё в разделе **ДОКУМЕНТИРОВАНО** — пересказ описаний методов и
приложений спецификации. Всё, что мы проверяли сами, помечено **ИЗМЕРЕНО**. Там, где спецификация
молчит, написано **ДАННЫХ НЕТ** — это полезнее догадки.

---

## 1. Главное: отмены две, и выбор между ними стоит денег

**ДОКУМЕНТИРОВАНО.** В API нет одного метода «отменить заказ». Есть два разных, и спецификация
прямо предупреждает, что применение неподходящего приводит к начислению операций.

| | `DELETE /v2/orders/{uuid}` | `POST /v2/orders/{uuid}/refusal` |
|---|---|---|
| Название в спецификации | Удаление заказа | Регистрация отказа |
| Когда применимо | пока груз не двигался по складу СДЭК, то есть в статусе «Создан» | в любом статусе, пока не установлен «Вручен» или «Не вручен» |
| Что происходит с заказом | заказ удаляется из системы | заказ возвращается в интернет-магазин; статус переходит в `NOT_DELIVERED` («Не вручен») с дополнительным статусом код 11 «Возврат, отказ от получения: Без объяснения» |
| Деньги | нет указаний на начисления | **спецификация не рекомендует применять к заказам в статусе «Создан»: по ним будут начислены операции и заказы попадут в Акт оказанных услуг** |
| Тело запроса | нет | нет |
| Ответ | `202 Accepted` | `202 Accepted` |

**Вывод, на который опирается вся конструкция:** «отказ» — это не отмена, а **возврат**. Посылка
физически едет обратно, и это оплачиваемая операция. «Удаление» — настоящая отмена, но она доступна
только в узком окне до попадания груза на склад отправителя.

Третий метод — `POST /v2/orders/{uuid}/clientReturn`, «Регистрация клиентского возврата» — к отмене
отношения не имеет: это возврат, который оформляет **покупатель после вручения**. В задаче отмены не
участвует.

## 2. Граница окна: по статусам из Приложения 1

**ДОКУМЕНТИРОВАНО.** Приложение 1 «Статусы заказов», первые строки:

| Status code | Code | Статус | Что означает |
|---|---|---|---|
| 0 | `ACCEPTED` | Принят | заказ создан в системе СДЭК, но требуются дополнительные валидации |
| 1 | `CREATED` | Создан | заказ зарегистрирован в базе данных СДЭК |
| 2 | `REMOVED` | Удален | заказ отменён интернет-магазином после регистрации и **до прихода груза на склад СДЭК в городе-отправителе** |
| 3 | `RECEIVED_AT_SHIPMENT_WAREHOUSE` | Принят на склад отправителя | оформлен приход на склад в городе-отправителе |
| 4 | `DELIVERED` | Вручен | конечный статус |
| 5 | `NOT_DELIVERED` | Не вручен | конечный статус |

Отсюда границы читаются однозначно:

- **до статуса 3** — работает `DELETE`, результатом становится статус `REMOVED`;
- **со статуса 3 и далее, пока не 4 и не 5** — только `refusal`, то есть платный возврат;
- **на 4 или 5** — недоступно ничего.

## 3. Обе операции асинхронные — тот же приём, что и при создании заказа

**ДОКУМЕНТИРОВАНО.** Оба метода отвечают `202 Accepted` с конвертом
`ResponseDtoRootEntityDto`:

```
{
  "entity":  { "uuid": "<идентификатор заказа>" },
  "requests": [
    {
      "request_uuid": "<uuid запроса>",
      "type":         "CREATE | UPDATE | DELETE | AUTH | GET | CREATE_CLIENT_RETURN",
      "date_time":    "<когда установлено текущее состояние>",
      "state":        "ACCEPTED | WAITING | SUCCESSFUL | INVALID",
      "errors":   [ { "code", "additional_code", "message" } ],
      "warnings": [ { "code", "message" } ]
    }
  ],
  "related_entities": [ ... ]
}
```

Значения `state`, как их описывает спецификация: `ACCEPTED` — предварительная валидация пройдена,
запрос принят; `WAITING` — ждёт обработки, зависит от другого запроса; `SUCCESSFUL` — обработан
успешно; `INVALID` — обработан с ошибкой.

**Следствие для кода: `202` НЕ значит «отменено».** Он значит «запрос принят». Подтверждение —
только опрос `GET /v2/orders/{uuid}` до `SUCCESSFUL` либо до появления статуса `REMOVED`. Это тот же
приём create-then-poll, который уже реализован у нас для создания заказа.

**ДАННЫХ НЕТ / ИЗМЕРИТЬ:** в перечислении `type` **нет значения для отказа** — перечислены только
CREATE, UPDATE, DELETE, AUTH, GET, CREATE_CLIENT_RETURN. Какой `type` приходит на `refusal`,
спецификация не говорит. Значит опрос по `type` писать нельзя, пока не измерено; опираться на
`request_uuid` и на статус заказа.

## 4. Ошибки

**ДОКУМЕНТИРОВАНО.** Оба метода на неуспех отвечают `400 Bad Request` с транспортом
`{ errors: [ {code, additional_code, message} ], warnings: [ {code, message} ] }`.
Конкретных кодов ошибок для «удалять уже поздно» спецификация не перечисляет.

**ДАННЫХ НЕТ / ИЗМЕРИТЬ:** что именно возвращает `DELETE`, если груз уже двинулся, — отдельный код
ошибки, или `202` с `state: INVALID` и ошибкой внутри `requests[]`. От этого зависит, где в нашем
коде живёт ветка «слишком поздно».

## 5. Про деньги — прямо и без домыслов

**ДОКУМЕНТИРОВАНО.** Единственное денежное утверждение об отмене во всей спецификации — то самое
предупреждение к методу отказа. **Никакой шкалы стоимости отмены, штрафов или тарификации отмены в
документе нет** (проверено поиском по «штраф», «стоимость отмены», «тарифицир», «начислен»,
«Акт оказанных услуг»).

**Что из этого следует для формулировок в кабинете:** ОСО может честно сказать, что отказ —
операция оплачиваемая, и **никогда не может назвать сумму**. Сумма живёт в договоре продавца со
СДЭК и в Акте оказанных услуг, а не в API.

## 6. Как это ложится на уже существующий код ОСО

- `REMOVED` → `CANCELED` — **уже есть** в `cdek/map-status.ts`. Успешное удаление отобразится само.
- `NOT_DELIVERED` → `RETURNED` — **уже есть**, решение от 05.08. То есть после отказа продавец
  увидит «Возврат», а не «Отменён». Это правда, и менять не нужно.
- Синхронизация статусов СДЭК зарегистрирована, значит подтверждение отмены придёт обычным путём,
  без отдельного механизма.
- Живая проверка пути `DELETE` есть на чём провести прямо сейчас: заказ в песочнице edu
  `a98b813e-01d4-4af5-8dde-8f0f5077620d` (отправление `cmsfv5rhh0001tzi0glbgn2pk`) — статус «Создан»,
  то есть ровно то окно, где удаление разрешено.

## 7. Что осталось измерить (три вопроса, все на песочнице edu)

1. Что возвращает `DELETE` на заказе в «Создан» — код ответа, конверт, и через сколько статус
   становится `REMOVED`.
2. Что возвращает `DELETE` на заказе, который уже двинулся, — код ошибки или `INVALID` внутри
   `requests[]`.
3. Какой `type` приходит в `requests[]` на `refusal`.

Ни один из трёх не требует боевого контура и не создаёт заказов.
