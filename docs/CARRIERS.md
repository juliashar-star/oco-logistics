# Перевозчики — карта, возможности, контуры

**Точка восстановления.** Этот файл нужен, чтобы человек, ничего не знающий об интеграциях
OCO, за несколько минут понял: какие перевозчики есть, что каждый умеет, на каком контуре он
живёт и **где лежит всё остальное**.

**Он владеет ровно четырьмя вещами** — картой, матрицей возможностей, контурами и указателем.
Всё прочее — эндпоинты, статусные модели, решения, лимиты, планы — живёт в других файлах, и
здесь на них только ссылки. Это правило, а не стиль: пересказ чужого факта не имеет даты,
читается как текущий и расходится с оригиналом молча. Каждая строка здесь проверена вопросом
«если это станет неправдой, кто-нибудь заметит?» — то, что не прошло, стало ссылкой.

**Состояние на коммит `f613058`** (`feat(offers): the offers response says which card should
be preselected`). На нём: **18 миграций**, `test:unit` — **1506**, `test:db` — **105**. Числа
верны для этого коммита, а не для «сегодня».

## 1. Карта: четыре адаптера, три API

Единица, вокруг которой всё построено, — не «перевозчик», а **услуга** (`orderAdapterKey`).
Их четыре, и они перечислены в `packages/core/src/carrier-adapter/order-adapters.ts`.

| Ключ адаптера | `providerKey` | Что это | API |
|---|---|---|---|
| `yataxi:next_day` | `yataxi` | «Доставка по России», адаптер **по умолчанию** | Яндекс, семейство `request/*` + `offers/*` |
| `yataxi:express` | `yataxi` | доставка в тот же день | Яндекс, семейство `claims/*` |
| `yataxi:courier` | `yataxi` | лёгкие посылки в тот же день | Яндекс, семейство `claims/*` |
| `cdek:delivery` | `cdek` | «Доставка по России» | СДЭК, `/v2/*` |

**Три записи из четырёх делят один `providerKey`.** Поэтому подключение перевозчика и выбор
услуги — разные вещи: одни учётные данные `yataxi` открывают три услуги. Из этого же следует,
что имя перевозчика не может сказать, о какой услуге речь, — на экране всегда пара
«перевозчик · услуга».

### Два семейства Яндекса — это два РАЗНЫХ API

Разные хосты, разные пути, разные учётные данные и разная авторизация. Общего у них только
слово «Яндекс» и `providerKey`.

**ИЗМЕРЕНО 27.08.2026, и это лучшее доказательство, какое у нас есть.** В одном прогоне
экрана офферов, одним продавцом, в одну минуту:

- `yataxi:next_day` — **дошёл до Яндекса и получил HTTP 500**, то есть авторизация прошла, а
  сервис ответил ошибкой;
- `yataxi:express` и `yataxi:courier` — **HTTP 403**, отказ авторизации.

**Одно семейство может быть отключено, пока второе отвечает.** Это не предположение из
документации, а наблюдение: 403 и 500 пришли одновременно по одному и тому же аккаунту.
Практическое следствие: «Яндекс не работает» — бесполезная формулировка, всегда надо
спрашивать, какое семейство.

**НЕ ИЗМЕРЕНО:** почему именно 403 — истёк ли токен Экспресса, отозван ли доступ, или дело в
чём-то ещё. Из ответа это не следует, и гадать нельзя.

### Может ли ОДИН аккаунт работать с обоими семействами — вопрос НЕ ЗАКРЫТ, а ОПРОВЕРГНУТ во времени

Это самая полезная запись во всём разделе, потому что два замера с разницей в месяц говорят
разное, и знать это важнее, чем иметь удобный ответ.

**16.07.2026, со слов поддержки Яндекса.** Аккаунт можно интегрировать только с ОДНИМ типом —
либо «Экспресс», либо «Доставка в другой день».

**31.07.2026, замер из документа того же дня. СЕГОДНЯ НЕ ПЕРЕСНИМАЛСЯ.** Один боевой токен
успешно отработал против ОБОИХ хостов: `offers/calculate` и `claims/create` на
`b2b.taxi.yandex.net`, `warehouses/list` на `b2b-authproxy.taxi.yandex.net` — **везде
HTTP 200**. То есть замер прямо противоречил тому, что сказала поддержка.

**27.08.2026, замер наш** (см. выше): на том же аккаунте `next_day` авторизовался и получил
**500**, а `express` и `courier` — **403**.

**Вывод ровно в ширину доказательств.** «Один токен работает с обоими» — это **датированное
наблюдение, которое сегодня не воспроизводится**, а не закрытый ответ. Возможных объяснений
несколько, и ни одно не измерено: токен Экспресса истёк; доступ отозван; либо ограничение,
о котором говорила поддержка, существует и просто проявилось позже. **Почему именно 403 —
НЕ ИЗМЕРЕНО.**

**Практическое следствие.** Пока это не выяснено, нельзя опираться ни на «у нас один токен на
всё», ни на «нужны два аккаунта». Оба утверждения сегодня недоказаны, и любой план, который
на одно из них опирается, надо считать построенным на песке. Вопрос остаётся открытым и
адресован перевозчику.

## 2. Матрица возможностей

Источник — `ORDER_ADAPTERS` в `packages/core/src/carrier-adapter/order-adapters.ts`,
`PICKUP_POINT_ADAPTERS` в `pickup-point-adapters.ts` и `STATUS_SYNC_ADAPTERS` в
`status-sync-adapters.ts`. **Матрица сверяема с кодом**: наличие возможности — это наличие
соответствующего поля у записи адаптера.

| Возможность | `yataxi:next_day` | `yataxi:express` | `yataxi:courier` | `cdek:delivery` |
|---|---|---|---|---|
| Котировка (`getOffers`) | ✓ | ✓ | ✓ | ✓ |
| Создание заказа (`confirmOffer`) | ✓ | ✓ | ✓ | ✓ |
| Отмена (`cancelOrder`) | ✓ | ✓ | ✓ | ✓ |
| Этикетка (`generateLabels`) | ✓ | ✗ | ✗ | ✗ |
| Акт приёма-передачи (`getHandoverAct`) | ✓ | ✗ | ✗ | ✗ |
| Синхронизация статусов | ✓ | ✓ | ✓ | ✓ |
| Доставка В ПВЗ | ✓ | ✗ | ✗ | ✓ |
| Термосумка | ✗ | ✓ | ✓ | ✗ |

**Список ПВЗ — свойство ПЕРЕВОЗЧИКА, а не услуги.** `PICKUP_POINT_ADAPTERS` ключуется по
`providerKey`, и точки умеют отдавать оба: `yataxi` и `cdek`. Это отдельная строка от
«доставки в ПВЗ»: Экспресс умеет показать точки Яндекса, но доставить в них не может.

**Почему Экспресс не возит в ПВЗ — это факт СХЕМЫ, а не замер.** В теле расчёта `claims/*`
нет поля для идентификатора точки, поэтому такой адрес назначения там невыразим в принципе.
Отмечено в коде как `servesPointDestination: false`.

**Чего в матрице нет намеренно:** процентов готовности. Процент — это число, которого никто
не мерил; оно устаревает молча и создаёт ложную точность. ✓ / ✗ / «не измерено» несут ту же
информацию и не гниют.

## 3. Контуры и учётные данные

### На каком контуре мы сейчас

**Только песочницы.** Переменная `OCO_CARRIER_CONTOUR` принимает ровно два значения,
`sandbox` и `production`, и проверяется **на старте процесса**: при несовпадении контура и
хоста приложение отказывается стартовать. Известные песочничные хосты перечислены в коде явно
(`packages/core/src/carrier-adapter/carrier-contour.ts`), боевые **намеренно не перечислены** —
гвард знает, как выглядит песочница, и всё остальное считает боем.

Три переменные с базовыми адресами: `CDEK_BASE_URL`, `YANDEX_DELIVERY_BASE_URL`,
`YANDEX_EXPRESS_BASE_URL`. Последние две различаются только на бою — поэтому их и две.

**Актуальные значения здесь не приводятся: их надо читать из окружения.** Записанное значение
устареет при первом же переключении, а прочитанное — нет. Перед любым вызовом, который пишет,
резолвнутый base URL печатается (правило из `CLAUDE.md`).

### Где лежат учётные данные

**Учётные данные перевозчиков — В БАЗЕ, у компании, зашифрованные.** Таблица
`CarrierCredential`: `companyId`, `providerKey`, `credentialsEnc`. Расшифровка — ключом из
`CARRIER_CREDENTIALS_ENCRYPTION_KEY` с солью `oco-carrier-credentials-v1`. Это прямое
следствие модели F: продавец подключает СВОИ договоры, поэтому его ключи принадлежат ему, а не
платформе, и одного набора «ключей OCO» не существует.

**В `.env` учётных данных перевозчиков НЕТ.** Там — базовые адреса, контур и ключи шифрования.
Ни `CDEK_ACCOUNT`, ни `CDEK_SECURE_PASSWORD`, ни яндексовского токена путь заказа оттуда не
читает.

**Две оговорки, чтобы утверждение было точным, а не почти точным:**

- **APIShip — исключение, и он не на пути заказа.** Его логин и пароль в `.env` есть. Это
  легаси-слой знания, а не исполнение; подробности — в `docs/APISHIP_INTEGRATION.md`.
- **`YANDEX_PROD_TOKEN` в `.env` задан, но НЕ ЧИТАЕТСЯ НИЧЕМ** — поиск по репозиторию не
  находит ни одного обращения к нему. Боевой по названию токен, лежащий без потребителя,
  стоит либо убрать, либо объяснить.

**Правило, которое не должно теряться:** где лежат боевые учётные данные для пробы — не
угадывать, а спрашивать человека и читать во время выполнения. Подробности и цена ошибки —
в `docs/LIVE_ENVIRONMENT_TASKS.md`, в самом начале.

## 3a. Ловушки контуров — читать до того, как планировать пробу

Четыре. Три уже удерживаются кодом, и здесь сказано чем; четвёртая не удерживается ничем и
поэтому опаснее остальных.

### ПЕСОЧНИЦА ПОДДЕЛЫВАЕТ `taxi_class` — и это ничем не удерживается

Тестовый контур возвращает **один и тот же набор офферов**, переклеивая на него класс. То
есть на tst `courier` и `express` выглядят одинаково не потому, что они одинаковы, а потому
что контур отдаёт одно и то же.

**Любой вывод о РАЗЛИЧИИ классов, сделанный на песочнице, недействителен.** Это касается
целой категории вопросов: чем `courier` отличается от `express` для отправителя, различаются
ли цены, различается ли транспорт, что означает `description` у оффера. Ни один из них не
проверяется на tst — только на бою.

**Ничто в коде это не ловит**, потому что ловить нечего: ответ синтаксически корректен и
выглядит правдоподобно. Единственная защита — знать об этом заранее, поэтому запись здесь.

**Усугубляющий факт:** у обоих семейств **ОДИН И ТОТ ЖЕ тестовый хост**
(`infra/.env.example`), так что на песочнице их не различить даже по адресу.

### Никогда не переставлять `YANDEX_*_BASE_URL` ради зонда

Базовый адрес — единственное, что отделяет клик в кабинете от боевого контура. Перевести
переменную «на минуточку» значит направить туда весь кабинет, включая чужие нажатия.

**Чем удерживается:** `checkCarrierContourStartup` в
`packages/core/src/carrier-adapter/carrier-contour.ts` — проверка на старте процесса,
приложение **отказывается стартовать** при несовпадении контура и хоста.

**Как правильно:** боевой хост кладётся **литералом во временный скрипт**, который живёт вне
репозитория и удаляется после прогона. Так делалась проба СДЭК 26.08 — метод описан в
`docs/research/cdek-tariff-limits-edu-2026-08-26.md` §8.

### Боевые хосты у семейств РАЗНЫЕ, и один из другого не получается

Нельзя вывести боевой адрес, удалив «tst» из тестового: у «Доставки по России» боевой хост —
`b2b-authproxy.taxi.yandex.net`, у Экспресса — `b2b.taxi.yandex.net`. Это разные адреса, а не
разные пути на одном.

**Чем удерживается:** тем, что переменных **две** — `YANDEX_DELIVERY_BASE_URL` и
`YANDEX_EXPRESS_BASE_URL`. Комментарий рядом с ними в `infra/.env.example` говорит прямо:
различаются они только на бою, и ровно поэтому переменные раздельные.

### Экспресс не работает в ПВЗ — проверять его на ПВЗ-заказе бессмысленно

Проверка любой экспрессовой функции на заказе с ПВЗ ничего не покажет: адаптер откажет ещё
до сети. **Тип доставки надо указывать первой строкой в плане любой проверки Экспресса.**

**Чем удерживается:** ранний возврат в `getExpressOffers`
(`packages/core/src/carrier-adapter/yandex/express-client.ts:400–405`) и поле
`servesPointDestination: false` у обеих экспрессовых записей в `order-adapters.ts`.

**Это факт СХЕМЫ, а не наблюдение песочницы** — в теле расчёта `claims/*` нет поля для
идентификатора точки. Комментарий в коде специально предупреждает: не «чинить» это подбором
географии и не выдумывать сопоставление станций.

## 4. СДЭК: исправление, а не обновление

Более ранние записки утверждали, что кода СДЭК нет и интеграция не начиналась. **Это неверно,
причём наоборот.**

**Что есть.** Четырнадцать модулей в `packages/core/src/carrier-adapter/cdek/`, около 2 800
строк, покрытых двадцатью тестовыми файлами. Шесть живых возможностей: котировка, создание
заказа, история заказа, сведения о заказе, отмена и список ПВЗ. Адаптер подключён в
`ORDER_ADAPTERS` как `cdek:delivery` и в `PICKUP_POINT_ADAPTERS` как `cdek`. Вокруг них —
слияние двух вызовов калькулятора, откат на код города, опрос состояния заказа, карта окна
отмены и транспорт с кэшем OAuth-токена. В базе лежат учётные данные, подключённые
03.08.2026. Четыре исследовательских файла в `docs/research/` описывают замеры, включая один
боевой прогон.

**Чего нет.** **Печатных форм** — колонка «Этикетка» показывает «Пока недоступна», и это
единственная услуга из четырёх без этикетки. **Потарифных лимитов** — объявлен один предел
веса на перевозчика, а не на тариф.

Числа и границы здесь не повторяются: они в файлах, на которые указывает §5.

## 6. Как поддерживать этот файл

**Он меняется, когда меняется КАРТА, а не когда меняется факт о перевозчике.** Новый адаптер,
новая возможность у существующего, смена контура, переезд учётных данных — сюда. Новый
эндпоинт, новый статус, новый замер, новое решение — в свой файл, а сюда максимум ссылка.

**Матрицу можно сверить с кодом за минуту**, и это единственный способ узнать, не устарела ли
она: возможность есть тогда и только тогда, когда у записи адаптера есть соответствующее поле.

**Шапку со ссылкой на коммит обновлять вместе с содержимым.** Она существует, чтобы читатель
видел, к какому состоянию репозитория относится написанное, — «сегодня» этого не сообщает.
