# Roadmap — OCO Logistics (MVP)

План по вехам. Каждая веха — самостоятельный кусок, который можно показать и проверить.
Сроки указаны для работы в одиночку с Cursor (ориентир — 6–8 недель). Cursor использует
этот файл, чтобы понимать порядок работ и не забегать вперёд.

Правило: **не начинаем следующую веху, пока предыдущая не проверена руками.**

# Перед запуском — сводный список

**Заведён 03.09.2026. Он НИЧЕМ НЕ ВЛАДЕЕТ.** Это указатель: каждая строка ссылается на то
место, где пункт записан сегодня, и исходные строки остаются там, где они есть. **При
расхождении верна исходная строка, а не эта сводка** — сводка стареет молча, и заводилась она
не для того, чтобы стать пятым реестром.

**Зачем он.** Предзапусковая работа лежала в четырёх местах — `docs/ROADMAP.md` (веха M4 и
«Открытые хвосты»), `docs/master-plan.md` (фазы P0-DOC, P0-OPS, P1, P2), `docs/DEFERRED.md`,
`docs/LAWYER_QUESTIONS.md` — и на вопрос «что можно делать сегодня» ни одно из них не
отвечало. Восемь вещей были записаны по два-пять раз каждая, и ни одна — целиком.

**Почему группы по ЗАВИСИМОСТИ, а не по теме.** По теме сгруппированы существующие файлы,
и именно поэтому список открытого в них нечитаем: чтобы выбрать работу, приходится
перебирать всё. Здесь ответ на один вопрос — **что не заблокировано прямо сейчас**.

**Правило для пункта с двумя зависимостями:** строка одна, и стоит она в группе того гейта,
который откроется ПОЗЖЕ; второй назван в самой строке. Порядок гейтов не назначен здесь — он
взят из `docs/master-plan.md` §6: «Затем → Фаза P1 (хостинг) → Фаза P2 (юрист + РКН) → первый
пилот».

**Номеров у строк нет, и это решение.** Номер — обещание стабильности, на него начинают
ссылаться. Раздел будет ужиматься по мере закрытия пунктов, и своя нумерация стала бы
четвёртой рядом с хвостами 1…32, `P0-*`/`P1-*`/`P2-*` и `Ю1…Ю12` — и однажды её пришлось бы
перенумеровать. Идентичность строки — те номера, на которые она ссылается.

**Мёртвых здесь нет** — десять закрыты 03.09.2026 пометками на своих местах. **Помеченного
`[позже]` самими файлами здесь тоже нет:** P2-LAW5 (зарубеж-опция), P3-*, хвост 5 (Registry
v2), хвост 17 (гео-разбивка).

Цель: доработки и перевозчик-специфичные возможности, отложенные до стабильного M4.
Не начинаем, пока M4 не проверен руками и пилоты не работают.

- Автоматический расчёт объёма отгрузки
  - Объём вычисляется автоматически из габаритов мест (длина × ширина × высота), не вводится вручную.
  - Для MVP — сумма объёмов мест (коробок), а не товаров. Учёт упаковки и пустот — отдельно, позже.
  - Контекст: некоторые перевозчики (например, Яндекс.Доставка) требуют объём в м³ при создании отгрузки.

- Поле фото товара (photoUrl) и проброс фото перевозчику
  - Добавить опциональное поле photoUrl у товара (публичная ссылка на изображение, валидный URL до 2048 символов).
  - Проброс фото — перевозчик-специфичная опция. На текущий момент в документации APIShip передача фото описана только для Яндекс.Доставки (поле item.photoLinks → photo_links, только тарифы «Доставка в другой день», только при создании заявки, не при редактировании, не для Cargo/Express).
  - Для других перевозчиков поддержку проверять индивидуально при подключении.

- Слой перевозчик-специфичных полей при создании отправления
  - Универсальная форма создания отправления не покрывает все случаи: у каждого перевозчика свои дополнительные поля и опции (у Яндекса — планирование отгрузки, объём/вес отгрузки, опция «нужна помощь с погрузкой», повтор по дням недели; передача фото; и т.п.).
  - Нужен слой, который добавляет перевозчик-специфичные поля поверх базовой формы.
  - Это архитектурное решение, проектировать отдельно после MVP.

## После MVP — направление развития (Phase 2)
НЕ строим сейчас; это записано, чтобы строить MVP с прицелом на будущее (см. docs/DECISION_ENGINE.md).
Браться за это — только после того, как MVP подтверждён на пилотных брендах.
- Правила автовыбора перевозчика по условиям (вес, габариты, тип доставки, регион, категория) —
  с интерфейсом настройки для продавца.
- Автоматический режим без ручного выбора для крупных продавцов (сотни заказов в день):
  пакетная обработка, фоновая очередь, идемпотентность, учёт лимитов APIShip.
- API для продавцов и массовый импорт заказов — два разных канала: (а) собственный сайт/магазин
  продавца (Tilda, InSales, свой движок и т.п.), который передаёт заказ в OCO через API/вебхук без
  ручного ввода; (б) интеграции с маркетплейсами и массовый CSV-импорт. Для MVP продавец всегда
  вводит адрес сам, вручную, в кабинете — на основе того, что покупатель указал в его канале продаж.
- Публичная страница/ссылка для покупателя (без входа в систему), где он сам вводит свой адрес
  и желаемое время доставки, минуя продавца. Снижает ручной труд при больших объёмах, но требует
  отдельной защищённой публичной формы, защиты от спама и канала доставки ссылки (SMS/мессенджер) —
  это отдельный продуктовый кусок, не часть логистического MVP.
- Расширенное использование полей APIShip (страховка, объявленная ценность, наличный расчёт и др.).
- Коэффициенты второго уровня: качество по региону и категории, стабильность срока,
  доля повреждений/потерь, штраф за просрочку.
